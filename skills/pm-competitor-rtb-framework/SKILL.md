# 竞品 RTB 链路拆解

对着一个竞品回答四个问题：它为谁、在什么场景、解决什么问题、凭什么被选中。最后收在「它没做到什么，我们要补什么」。

## 先定业务目标

确认这份分析服务哪个决策：产品定位、新品上市、营销传播，还是品牌升级。目标不同，拆解重点不同。用户没说时按产品定位处理。

主链路只服务产品定位。另外三个场景做简化处理：上市看节奏与内容策略，传播看策略与创意，品牌升级看它有没有发生。没有发生的场景直接写不适用，不硬凑内容。

## 取证

- 优先一手来源：官网各语言版本、应用商店页面、定价页、更新日志、帮助中心，并记录抓取日期。
- 正文抓不到时，先看页面内嵌的 JSON 状态，再考虑截图或前端 bundle。图片与脚本里的文案按实际读到的写，读不到就写不可得。
- 每个论断标出来源性质：公开页面上的事实，还是自己的推断。推断要写依据。
- 拿不到的信息写不可得，不要用行业惯例补齐，不要编数字。
- 正文里不放参考链接，把来源写进开头一句或写进句子里。

## 五步链路

**· 一、用户**

拆三层：画像（地域、设备、项目、水平、年龄、训练方式）、消费偏好（价格敏感度、决策依据、消费发生在什么时间）、潜在动因（控制感、焦虑缓解、奖励与补偿、自我实现、美感与自我呈现、归属与认同）。潜在动因最容易被跳过，也最能解释后面的取舍。最后收一句：用户真正买的是什么。

**· 二、场景**

分生活、情绪、社交三类，写明它覆盖了哪几类。判断场景价值：是高频刚需、低频高价值，还是自己造出来的新场景。再评场景是否清晰、是否具体、能否引起共鸣，并指出场景与交付节奏之间有没有矛盾。

**· 三、问题**

分痛点、痒点、爽点三类，逐条标注竞品解决了哪些、留下了哪些。爽点做得锋利是它的长处，痒点留口子通常是有意为之，要点出「它做得到但不愿意做」以及原因。

**· 四、解决方案**

拆三层：功能层写清能力与参数，以及这些能力合起来解决了什么；情绪层写它提供了什么确定性与安全感；社交层写它给了用户什么身份，还是主动放弃。三层对齐后，把没有被满足的部分列成缺口清单。

**· 五、支撑点（RTB）**

按技术证明、信任背书、口碑效应、设计与细节、品牌势能五项评强度，指出它靠哪一条腿站着，以及这条腿被追平那天会发生什么。

## 缺口清单

每条缺口写三件事：缺口是什么、它缺在哪一层、对应我们自己哪个需求编号。编号从 P1 起连续排，便于在需求池与 PRD 里被引用。

缺口要来自用户任务，不要来自功能清单的对齐。「竞品有 A 我们没有」不是缺口，除非能说清 A 服务于哪个没被满足的任务。

## 结论

按这个顺序写：

1. 用一句话说清这个产品的本质，并证明这句话能解释它全部的产品选择。
2. 按这条本质推断它接下来会做什么、不会做什么，指出哪一段是时间窗口。
3. 列出我们要做的动作，每条对应缺口编号与需求编号。
4. 给出落地顺序，说明为什么先做第一项。
5. 写明需要回避的方向。

## 写作规范

- 陈述句为主，一句话说一件事，不用感叹句与动员句。
- 推断必须带标记，读的人要能分清哪些是官网写的、哪些是判断。
- 数字只在有出处时使用，能写具体就不写模糊。
- 不放参考链接列表，也不加 emoji。
- 结论要落到编号与顺序，停在「值得学习」这类句子上等于没写。

## 与其他技能配合

- 需要横向对比多个竞品时，用 `pm-competitor-deconstructor`。
- 需要把任务拆得更细并排序时，用 `pm-competitor-jtbd`。
- 需要对外交付文档时，用 `zh-factual-writing` 校准语气；需要产品需求文档时，用 `prd-writer-zh`。

## 交付前自检

- 每句话都能追到官网、商店页或文档，没有凭空出现的能力与指标。
- 推断项标注完整，没有把推测写成事实。
- 缺口清单指向用户任务，不指向功能对齐。
- 结论包含可执行动作与先后顺序。
- 不适用的场景已经写明不适用，没有硬凑内容。
