## 1. Executive Summary

我们为 **以技术动作进阶为目标的业余抱石爱好者** 做一款 **AI 攀爬动作分析工具**，解决 **"这一挂哪里发力浪费了、为什么失败，只有岩馆教练在场才说得清"** 的问题——它把攀爬视频变成一份带 `[MM:SS]` 时间戳、可反复回看、可导出的教练式点评。

**一句话版本：**

> 上传一段抱石视频，得到带时间戳的 AI 动作点评、评分与专项改进建议，并留下可对比的训练历史。

**本次迭代（v2.0）要交付的结果：**

| 方向 | 一句话目标 | 状态 |
|------|-----------|------|
| 可信 | 分析结果稳定可解析，失败时用户知道"为什么、等多久、怎么办" | 🔄 部分达成，需指标验证 |
| 可复用 | 历史、收藏、进步曲线、PDF 报告形成闭环，用户愿意第二次上传 | 🔄 功能齐备，缺留存数据 |
| 国内可用 | 桌面端 + 国产模型（DeepSeek）绕开境外服务可达性问题 | ✅ 桌面版已具备，⚠️ 抽帧方案有精度代价 |

> 🔶 **Assumption**：本节中"用户愿意第二次上传"是基于产品机制的推断，尚无真实使用数据支撑。详见 [Section 10](#10-open-questions)。

## 2. Problem Statement

### Who Has This Problem?

- **主要是**：有 1 年以上抱石训练经历、把攀爬当作技术运动而不仅是社交活动的爱好者（能力带大致 V2–V6）。
- **次要地**：刚入门、还分不清"是力量不够还是动作不对"的新手（V0–V2）。
- **明确不是**：追求竞技成绩的运动员——他们有教练团队与录像分析流程。

> 🔶 **Assumption**：能力带 V2–V6 是"最缺反馈又最愿意自己找反馈"的区间。该推断来自常识（新手缺基础训练量、高手有教练资源），未经验证。

### What Is the Problem?

抱石的进步瓶颈是**动作质量**，而动作质量**只能被旁观者看见**——攀爬者本人在墙上感受不到自己的重心偏移、脚点浪费与发力顺序。

当前替代方案都有明显缺口：

| 替代方案 | 缺什么 |
|----------|--------|
| 岩馆教练现场点评 | 贵、需要对方在场、无法反复回看 |
| 自己拍视频回看 | 只能看出"摔了"，看不出"哪一步开始错的" |
| 找同伴帮忙看 | 同伴不一定具备分析能力，也不好意思反复麻烦别人 |
| 直接问通用大模型（贴视频/截图） | 能得到内容，但**得不到产品**：没有上传约束处理、没有长任务管理、没有结构化报告、没有历史、没有导出 |

### Why Is It Painful?

- **用户影响**：同一个动作错误会重复数月；训练量在涨，动作效率没涨，慢慢消耗训练热情。
- **过程影响**：一次攀爬只有 10–90 秒，但"想被点评"要等到下次有人在场——反馈周期从秒级变成天级甚至周级。
- **商业影响（若走向产品化）**：这类需求低频、非刚需、付费意愿不确定，必须靠**低边际成本**与**高留存替代价值**成立；目前没有证据表明存在规模化付费市场。🔵 待确认

### Evidence

> ⚠️ 本节是当前 PRD 最弱的一环：本产品尚无真实用户研究与使用数据。按模板纪律，此处不编造数据。

| 证据类型 | 现状 |
|----------|------|
| 用户访谈 | 🔵 **Open Question**：尚未做过结构化访谈。建议先跑 5 场 15 分钟访谈（可参考 `discovery-interview-prep` 的 Mom Test 提问法）。 |
| 产品数据 | 🔵 **Open Question**：没有埋点，无法统计分析成功率、二次上传率、429 失败占比。 |
| 社群信号 | 🔶 **Assumption**：攀岩社群中"求点评""这挂怎么破"类帖子常见——属于个人观察，未做系统采样。 |
| 客户原话 | 🔵 **Open Question**：无。**在补齐访谈原话前，本节的问题真实性仍属未验证。** |

> **结论**：问题方向有强合理性（旁观者视角是客观盲区），但**证据等级是"合理推断"而非"已验证"**。这是本 PRD 需要优先补足的部分，也是 [Section 10](#10-open-questions) 的第一条。

## 3. Target Users & Personas

### Primary Persona

- **Name**：小林（28 岁，上海）
- **Role**：互联网公司产品/研发岗，每周去岩馆 2–3 次，规律训练约 2 年
- **Context**：能力 V4–V5；有手机、会用 Notion/Strava 类记录工具；**没有固定教练**，偶尔参加岩馆团课
- **Goals**：把一条挂爬得更省力、把 V5 稳定下来、看到自己的长期进步
- **Pain points**：知道自己"某一步开始就乱了"，但说不清是哪一步；摔了几次后开始怀疑是不是力量不够
- **Current behaviour**：用手机拍下整条线 → 回家翻看 → 觉得"再看也没用" → 删掉；偶尔发到群里求点评，通常没人认真回

### Secondary Persona

- **Name**：阿哲（35 岁）
- **Role**：岩馆兼职教练
- **Differs from primary**：他要的是**给别人讲清楚**，需要结论可复述、可截图分享；对"AI 说得对不对"更敏感，会挑错
- **用途**：把 AI 报告当备课/复盘素材，或给学员做对比

> 🔶 **Assumption**：教练是否真的会用第三方 AI 报告存疑（专业自尊 + 已有自己的判断体系）。这属于**价值风险**，需要先访谈验证，而不是直接投入开发教练端功能。

### Jobs-to-Be-Done

- **Functional job**：在**没有人旁观**的情况下，拿到可执行、定位到具体动作节点的改进建议。
- **Emotional job**：不再把失败归因为"我力量不够"，而是获得"这是一个可修正的技术问题"的确定感；不想为看不懂的反馈浪费时间。
- **Social job**：在岩馆同伴/训练群里显得"训练是有方法的"，能拿报告做交流素材。

> 🔶 **Assumption**：Social job 的真实强度未验证——它决定"分享/导出"该被当作核心还是附属功能。

## 5. Solution Overview

### Solution Description

CRUX 抱石把"视频 → 教练式点评"包装成一条**可失败、可重试、可累积**的产品流水线，而不是一次性的 API 调用。

**核心流程（两种形态共用同一套分析逻辑）：**

1. 用户选择视频，填写难度（V0–V10）、爬升高度、备注。
2. 选择分析深度（`light` / `deep`）与 AI 输出语言（中文 / English，与界面语言独立）。
3. 浏览器侧压缩到约 3.5MB 以内（Vercel 请求体上限约 4.5MB）。
4. 生产环境走异步任务：写入 Blob → `waitUntil` 推进 Job → 客户端轮询状态。
5. 四段进度反馈：本地处理 → 上传 → 模型处理 → 生成分析。
6. 结果页呈现：时间轴点评、评分、难度、维度总结、改进要点；可收藏片段、导出单页 PDF。
7. 记录写入本地 IndexedDB（离线可用、含视频本体）；登录后镜像到云端，换设备可拉回。

**两种形态的分工：**

| 形态 | 技术栈 | 为什么存在 |
|------|--------|-----------|
| 网页版 | Next.js 16 App Router + Gemini | 零安装、可分享链接 |
| 桌面版 | Electron + React + Vite | 国内可达；可直连 DeepSeek（本地抽帧后提交关键帧） |

> ⚠️ **已知代价**：DeepSeek 路径不接受视频，客户端把视频均匀抽成 16 张关键帧并标注 `[MM:SS]` 后提交。**帧与帧之间的连续动作看不到**——这是用"可达性"换来的精度损失，属于设计取舍而非缺陷，但必须在文案中让用户可自主选择（要深度分析请切 Gemini）。

### Key Features

1. **时间轴点评**：严格 `[MM:SS]` 行格式，可按秒定位回原视频。
2. **异步任务 + 可理解失败**：429 显示冷却倒计时，配额耗尽给出明确文案，超时自动有限重试，用户可取消。
3. **结构化消费**：评分 / 难度 / 维度总结 / 改进块由二次解析产出，供 UI 与 PDF 复用。
4. **历史与收藏**：本地优先（IndexedDB，含视频 Blob），按日期/分数/关键词筛选。
5. **进步曲线**：按天汇总爬升高度与最高 V 级。
6. **导出**：单页 A4 风格 PDF 报告 / Markdown 全文。
7. **双语与主题**：中英界面、昼夜模式，AI 输出语言独立可选。
8. **Prompt 版本化**：`PROMPT_VERSION` 写入每条记录，支持后续回归与 A/B。

## 6. Success Metrics

> ⚠️ 本产品**没有埋点**，因此所有"当前值"都是估算或未知。按模板纪律，估算一律标注 🔶，未知一律标注 🔵——**没有基线就不设可信目标**，这是本节最重要的一句话。

### Primary Metric

- **Metric**：**分析成功率** —— 从点击"开始分析"到产出**非空且可解析**的报告的比例。
- **Current**：🔵 **未知**。🔶 主观估计 70–85%（主要失败来源为配额/限流与上传超限）。
- **Target**：≥ 90%（配额充足前提下）。🔶 目标值需在拿到真实数据后重新校准。
- **Timeline**：先补埋点，再测量 30 天。
- **为什么是它**：这是产品的**信任基准**——一次失败就足以让用户不再回来；"分析不准"是模型能力问题，"分析失败"是产品问题，后者必须先解决。

### Secondary Metrics

- **7 日内二次上传率**：🔵 未知。这是"有没有替代价值"最直接的信号；单次使用只能说明新鲜感。
- **PDF / 分享导出率**：🔵 未知。用来验证 [Section 3](#3-target-users--personas) 中 Social job 的强度。
- **单次分析平均耗时**：目标 1–3 分钟（依赖视频长度与模型排队）。
- **失效原因分布**：429 限流 / 配额耗尽 / 超时 / 上传超限 / 解析失败 各占多少——**这是最有行动价值的指标**，直接决定下一步做什么。

### Guardrail Metrics

- **单次分析成本与配额消耗**：不得因重试策略导致配额更快被击穿（免费档 RPM 与日配额是硬约束）。
- **上传失败率**：压缩失败时不上传，避免把 "Request Entity Too Large" 这类纯文本错误暴露给用户。
- **隐私边界**：分析记录默认留在本机；不得为提升"留存指标"而强制登录或强制上云。

## 7. User Stories & Requirements

### Epic Hypothesis

> 我们相信：对没有固定教练的业余抱石者，**提供带时间戳、可反复回看、可累积的 AI 动作点评**，会让"分析成功率"与"7 日内二次上传率"显著优于"什么都不做"——因为当前的替代方案要么昂贵、要么在时间上不可得。
> 我们会在埋点上线后，以 **分析成功率 ≥ 90%** 与 **7 日内二次上传率** 为准绳，在 30 天后验证该假设。

### User Stories

> 状态标记：✅ 已实现 · 🔄 部分实现 · ⏳ 未实现

---

**Story 1：上传视频并获得带时间戳的分析** ✅

作为一位没有教练在场的抱石者，我想上传一段攀爬视频并拿到逐段点评，这样我能知道"哪一步开始出问题"。

**Acceptance Criteria：**

- [x] 支持点击与拖拽选择视频；非法文件类型给出明确错误提示
- [x] 提交前可在浏览器侧压缩至约 3.5MB 以内，压缩失败有可见提示
- [x] 可填写难度（V0–V10）、爬升高度（米）、备注
- [x] 可选择分析深度 `light` / `deep`，并选择 AI 输出语言（中文 / English）
- [x] 输出包含严格 `[MM:SS]` 格式的时间轴行；空正文视为失败，不写入记录
- [x] 结果页可浏览时间轴、总结与全文

---

**Story 2：分析失败时我知道发生了什么、要等多久** ✅

作为用户，当分析因为限流或配额失败时，我想知道原因与等待时间，这样我不会以为产品坏了。

**Acceptance Criteria：**

- [x] 429 时解析并显示冷却秒数（或可理解的错误文案），支持重试
- [x] Job 状态区分 `completed` / `failed` / `rate_limited`
- [x] 日配额耗尽时给出明确文案，不做无限假重试
- [x] 后台卡死有超时检测与有限次自动重试（最多 3 次分析重试）
- [x] 用户可主动取消；取消后文案为"已取消"而非"失败"
- [x] 四段进度（本地处理 → 上传 → 模型处理 → 生成）在等待期间持续可见

---

**Story 3：回看与收藏关键片段** ✅

作为用户，我想把"这条挂的关键卡点"收藏下来，这样下次训练可以直接对比。

**Acceptance Criteria：**

- [x] 历史记录保存在 IndexedDB，含视频 Blob，离线可打开
- [x] 可按日期、分数、关键词筛选
- [x] 可收藏时间轴片段，并在收藏页汇总
- [x] 点击收藏条目可跳回原视频对应秒数

作为规律训练者，我想看到自己的爬升与难度趋势，这样我有继续记录的动力。

- [x] 以趋势曲线呈现
- [ ] 🔵 待确认：统计口径是否只统计"已完成"的攀爬？当前按用户填写的爬升高度汇总，**填错即污染曲线**，需要修正入口或明确说明

**Story 8：让分析质量可被验证与迭代** ⏳

作为产品维护者，我想在改动 Prompt 后知道质量是变好还是变差，这样我不会凭感觉调参。

**Acceptance Criteria：**

- [ ] 固定一组评测视频（建议 8–12 条，覆盖不同难度与失败模式）
- [ ] 每个 `PROMPT_VERSION` 在评测集上跑一次，记录分数与人工评分
- [ ] 改动 Prompt 时输出对比结论，而不是直接上线
- [ ] 🔵 待确认：人工评分标准如何定义（例如 1–5 分描述"建议是否具体可执行"）

### Constraints & Edge Cases

- **技术约束**：Vercel 单次请求体约 4.5MB → 视频本体限制 3.5MB；Serverless 单次执行约 60s → 必须异步化。
- **模型约束**：免费档有 RPM 与日配额；`generateContent` 单独计数；部分模型对免费 Key 配额为 0。
- **输入格式**：当前以自然语言叙述体输出，靠 `parseAnalysis` / `parseStructuredReport` 二次解析。🔵 是否改为固定 JSON Schema + zod 校验待评估（好处是稳，代价是输出可能变"僵硬"，损失教练口吻）。
- **边界情况**：用户在分析中途关闭页面；同一 Job 被重复推进（已有 `PIPELINE_LOCK_MS` 防护）；视频时长极短或极长；轮询中途断网。
- **数据边界**：IndexedDB 容量有限，大量视频会挤爆本地存储——🔵 需确认配额与清理策略。

## 8. Out of Scope

### Not Included in This Release

| 不做的事 | 理由 |
|----------|------|
| **姿态估计 / 骨架关键点分析** | 需要多机位或穿戴设备与校准流程，设备门槛远高于"拍一段视频"，与"零门槛"的定位冲突 |
| **实时分析（边爬边给反馈）** | 需要边缘算力与低延迟模型，与当前架构不兼容 |
| **社交 feed / 关注 / 评论** | 引入内容审核与运营成本，且不是"解决个人技术问题"的必要条件 |
| **付费订阅与计费系统** | 需求规模未验证；先验证留存，再谈收入 |
| **教练端功能（布置作业、学员管理）** | 教练是否会使用未验证（见 Section 3 的价值风险） |
| **iOS / Android 原生 App** | 网页版与桌面版已覆盖主要场景，原生开发对个人项目的持续维护成本不划算 |
| **国内云服务迁移（去 Vercel）** | 成本与工程量大；桌面版已提供可达性对策，优先级低于分析质量 |
| **医疗 / 康复 / 伤害诊断** | 明确越界：免责声明已说明仅供训练参考 |

### Future Considerations

- Provider 抽象（`AnalyzeProvider` 接口 + 环境变量切换）——**接口先定，实现不必齐**。
- 每人每日分析次数配额，保护 API 额度。
- 云端历史（当前已有基础镜像，合并策略补齐后可正式启用）。
- 若评测集证明"结构化输出不影响体验"，再评估切换到 JSON 输出。

## 9. Dependencies & Risks

### Dependencies

| 类型 | 依赖 | 说明 |
|------|------|------|
| 外部 · 模型 | Gemini API（`gemini-2.5-flash`） | 核心分析能力；免费档配额是硬约束 |
| 外部 · 模型 | DeepSeek API | 桌面版默认后端，国内可达；**不支持视频**，依赖本地抽帧 |
| 外部 · 基础设施 | Vercel（托管 / Blob / `waitUntil`） | 异步 Job 的运行前提；国内访问不稳定 |
| 外部 · 基础设施 | Supabase（Postgres + 迁移脚本） | 账号与云端记录；免费额度有限 |
| 内部 · 工程 | `lib/analyze-prompt.ts` 等核心模块 | Prompt 版本与解析层必须同步演进，否则记录不可回归 |
| 内部 · 数据 | 评测视频集与人工评分标准 | ⏳ 尚未建立，是 Story 8 的前置条件 |

### Risks & Mitigations

按模板要求覆盖 Cagan 的四类风险（价值 / 可用性 / 可行性 / 商业可行性）：

| 风险 | 类型 | 影响 | 对策 |
|------|------|------|------|
| 用户只试一次就不再使用 | **价值** | 产品沦为玩具，没有留存 | 先补埋点测 7 日二次上传率；用 5 场访谈验证"是否真的缺这类反馈" |
| 用户看不懂或不信任 AI 点评，觉得"说得虚" | **价值 + 可用性** | 报告再好看也不会被执行 | 建立评测集与人工评分（Story 8）；Prompt 强制"定位到具体秒数 + 具体动作" |
| Gemini 免费配额被击穿，频繁失败 | **可行性** | 直接摧毁"分析成功率"主指标 | 429 分类与冷却提示（已实现）；评估付费档或加每日配额；桌面版可切 DeepSeek |
| 抽帧方案精度不足，用户以为"AI 不准" | **价值** | 桌面版口碑受损 | 首次使用明确说明两种后端差异；深度分析引导到 Gemini |
| 模型输出格式漂移导致解析失败 | **可行性** | 记录写入失败 / 空白 | `PROMPT_VERSION` + 空响应检测（已实现）；评估 JSON Schema + zod |
| 国内用户打不开网页版 | **可行性** | 作品集不可达 | 以桌面版 + 录屏 + GitHub 为主要入口 |
| 记录只在本机，换设备丢失 | **可用性** | 用户放弃累积价值 | Supabase 镜像已具备；补齐冲突与删除语义后正式启用 |
| 隐私顾虑（视频上传给第三方模型） | **可行性 + 价值** | 用户不敢传真实视频 | 明确说明"记录默认存本机"；提供本地记录一键清除 |
| 个人项目时间投入不可持续 | **可行性** | 停在半成品状态 | 明确 L1（作品集）优先于 L2（产品化）；不对外承诺 SLA |

## PRD Self-Assessment

### Strongest Section

**Section 7（User Stories & Requirements）与 Section 9（Dependencies & Risks）**。
原因：这两节直接对应**已经存在的代码**与**已经踩过的坑**（异步 Job、429 分类、抽帧取舍、`oklab` 导出崩溃），验收标准可逐条回到仓库验证，不是纸面推演。

### Weakest Section

**Section 2（Problem Statement）的证据部分**。
原因：整份文档里，唯一无法用代码佐证的就是"用户真的有这个痛点、且愿意重复使用这个工具"。目前所有用户侧结论都是 🔶 假设或 🔵 待确认。**这不是写得不认真，而是事实如此——必须靠访谈与埋点补齐，不能靠措辞掩盖。**

### Top Assumptions to Validate

| # | 假设 | 所在节 | 若为假的后果 | 验证方式 |
|---|------|--------|--------------|----------|
| 1 | 无教练的爱好者确实需要"随时可得的动作反馈" | Section 2 | 产品失去存在前提 | 5 场 15 分钟访谈，问过去行为而非意愿 |
| 2 | 用户会重复使用（而非试一次） | Section 6 | 无留存，价值假设不成立 | 埋点测 7 日内二次上传率 |

### Recommended Next Step

> **在把本 PRD 交给任何人评审之前，只做一件事：补埋点，拿到"分析成功率"与"失效原因分布"的真实基线。**
> 理由：本 PRD 中所有指标目标都建立在 🔶 估算之上；而"失效原因分布"同时决定后续三件事的优先级——是修上传、修重试、换模型，还是改 Prompt。在这个数据到位之前，Section 6 的目标值不应被当作承诺。
