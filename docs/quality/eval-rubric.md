# 评测口径

## 1. 评什么

一条抱石视频的点评，按五个维度打 1-5 分：

| 维度 | 1 分 | 3 分 | 5 分 |
| --- | --- | --- | --- |
| 重心与身体位置 | 明显远离墙面，靠手臂拉住 | 大部分动作能贴墙，换脚时偶尔外摆 | 胯部主动贴墙，重心转移连续 |
| 发力与动作技术 | 只会直臂拉，技术动作缺失 | 能用折膝、侧拉，但方向或时机不稳 | 技术动作与发力顺序匹配动作意图 |
| 抓握与踩脚 | 脚点踩不住，频繁滑脚 | 能踩住主要脚点，细节需要调整 | 脚尖压住，换脚干净，手点不浪费 |
| 动作顺序与节奏 | 先拉后蹬，节奏断裂 | 大致顺序对，关键一步会抢 | 先移重心再出手，节奏稳定 |
| 完攀与收尾 | 最后一步失控或放弃 | 能收尾，但有明显多余动作 | 收尾干净，没有补债动作 |

评分不是“动作好不好看”，而是“这一次攀爬里，身体有没有把力量用在线上”。

## 2. 证据规则

每条点评必须满足三个条件，否则不计入有效点评：

1. 有时间戳，且落在 `0` 到视频时长加 2 秒之间。
2. 有画面线索，说明看到了什么，例如“右脚踩在岩点边缘”“挂旗前脚背蹭墙”。
3. 有下一步动作，说明下一次怎么做，例如“脚尖先压住再挂旗”，不能只写“注意重心”。

只有结论、没有画面线索的点评，按空话处理。

## 3. 标注流程

- 每条案例至少 1 名标注人；其中 8 条由 2 人独立标注，用来算一致性。
- 先各自打 5 维分，再合议分歧；合议后的分数作为金标。
- 标注时看不到模型输出，避免被模型措辞带偏。
- 案例标签里同时写“必须提到的线索”，例如这条线的关键动作是折膝、挂旗或侧拉。
- 视频不进仓库，只提交脱敏后的元数据、标签和输出文本。

## 4. 指标与门槛

| 指标 | 计算 | 红线 |
| --- | --- | --- |
| 可解析率 | 至少解析出一条合法时间戳片段的案例占比 | ≥ 98% |
| 契约完整率 | 可解析且给出总分的案例占比（v2 起同时要求 5 维分） | ≥ 98% |
| 时间戳可定位率 | 时间戳落在 `0` 到时长加 2 秒的比例 | ≥ 95% |
| 关键线索覆盖率 | 命中案例标签中动作词的比例 | 单案例 ≥ 60% |
| 空话率 | 含禁用句式的片段占比 | ≤ 30% |
| 重复片段率 | 归一化文本完全相同的占比 | ≤ 20% |
| 难度一致率 | 模型 V 级与标注一致的比例 | 只观察，不设硬门槛 |
| 维度分覆盖率 | 显式给出 5 维分的案例占比 | v2 起 ≥ 90% |
| 维度分 MAE | 与人工 5 维评分的平均绝对误差 | ≤ 1.0 |

综合质量分是内部加权，只用于版本间比较，不是行业基准。权重写在 `lib/eval-metrics.ts`，调整权重需要同步更新本文档。

「可解析率」和「契约完整率」必须分开看。前者衡量程序能不能读，后者衡量输出符不符合下游约定。真实基线里两个数字是 100% 和 0%，差距全部来自 Prompt 没有要求总分——把两者合成一个「格式合法率」会让这种规格问题看起来像模型能力问题。

## 4.1 输出契约 v2

v1 是自由文本，`score` 和 `dimensionScores` 靠模型自觉，实际 10/10 缺失。v2 改成单个 JSON 对象，schema 定义在 `lib/analysis-schema.ts`：

```json
{
  "grade": "V4",
  "score": 78,
  "dimensionScores": { "hips": 4, "power": 3, "feet": 4, "sequence": 3, "completion": 5 },
  "highlight": "起步那一脚踩虚了，后面都在补债",
  "segments": [{ "t": "00:03", "evidence": "看到了什么", "fix": "下一次怎么做" }],
  "dimensionSummary": ["重心与身体位置：…"],
  "improvements": [{ "title": "折膝方向", "practice": "…", "strength": "…" }],
  "overallAdvice": "一句话总结"
}
```

必须满足的字段：`score`（0-100）、`dimensionScores`（5 个 1-5 分）、`segments`（至少 1 条，含 `t`/`evidence`）。缺任何一个就判定为不是 v2 契约。

解析策略：先试 v2，失败回落 v1 的文本正则。回落是刻意的——历史记录、桌面端已入队的旧任务、模型偶发不守契约时，报告都还能读出来，只是拿不到分数。

开关：`lib/analyze-prompt.ts` 的 `ACTIVE_CONTRACT`。默认 `v1`，跑完真机对比并确认结构红线通过后再改 `v2`。

## 5. 案例格式

案例放在 `evals/cases/`，一条视频一个 JSON：

```json
{
  "id": "case-001",
  "title": "45 秒 V4 室内抱石，完攀",
  "durationSec": 45,
  "grade": "V4",
  "locale": "zh",
  "depth": "deep",
  "model": "gemini-2.5-flash",
  "labels": {
    "dimensions": {
      "hips": 4,
      "power": 3,
      "feet": 4,
      "sequence": 3,
      "completion": 5
    },
    "mustMention": ["折膝", "脚点", "胯部"],
    "notes": "双人标注合议后的金标"
  }
}
```

模型输出放在 `evals/fixtures/` 或候选目录，`caseId` 指向上面的案例。

## 6. 常见错误

- 把“没有提到”当成“提到了”：覆盖率只做字符串命中，同义词要在标签里写全。
- 用模型给自己打分：LLM-as-judge 可以做辅助，但不能替代人工金标。
- 只看平均分：一条 P0 坏案例会被高平均分盖住，所以 P0 单独计数。
- 样本太少就下结论：少于 3 条只输出“补样本”，不输出上线决策。
